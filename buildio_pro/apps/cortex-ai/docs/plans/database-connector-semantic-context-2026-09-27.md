# Database Connector Semantic Context and Query Tools Plan - cortex-ai

**Date:** 2026-09-27
**Status:** Planned
**Depends on:** `database-connectors-2026-09-15.md` Postgres connection and
table-browsing flow
**Scope:** Postgres schema synchronization, human-reviewed semantic metadata,
connector access policy, and safe AI query tools

## Goal

Turn a connected Postgres database into a governed data source that an AI agent
can understand and query reliably. The feature must combine discovered database
metadata with human-authored business context while preventing the model from
issuing arbitrary SQL or reading unapproved data.

The first usable release should let a workspace member:

1. Refresh a connector's schema.
2. Review tables, columns, keys, and relationships.
3. Add table and column descriptions and synonyms.
4. Choose exactly which tables and columns an agent may use.
5. Attach one approved connector to a chat thread.
6. Ask questions that are answered through constrained, audited read tools.

## Current baseline

- Postgres connections are workspace-scoped and store encrypted credentials in
  `lib/db/schema/connections.ts`.
- `lib/connectors/schema.ts` opens a temporary `pg.Client` and lists base tables
  from `information_schema`; metadata is not persisted.
- `GET /api/connections/:id/tables` returns only `{ schema, name }`.
- `/dashboard/agent/connectors/[id]` displays a flat table list with no detail or
  configuration UI.
- `app/api/chat/route.ts` currently exposes only knowledge-base tools and has no
  connector or thread-to-connector context.
- `chat_audit_logs` stores generic model tool calls/results, but there is no
  connector query audit with table, timing, row-count, or refusal metadata.

## Product decisions

- **Semantic layer, not descriptions only:** model context includes physical
  schema, descriptions, synonyms, approved relationships, and access policy.
- **Separate data classes:** discovered metadata, user-authored semantic context,
  and execution policy remain separate so refreshes cannot overwrite user work.
- **Review before use:** newly discovered tables are unavailable to AI tools until
  a workspace member explicitly enables them. Removed tables are disabled
  automatically but retain context for review or restoration.
- **Small generic tool surface:** provide schema discovery and structured query
  tools instead of generating one tool per table.
- **No arbitrary SQL in the MVP:** the server compiles a validated query spec to
  parameterized Postgres SQL. Raw model-generated SQL remains out of scope.
- **One connector per thread in the MVP:** this avoids ambiguous table names and
  cross-database joins. The server authorizes the selection on every request.
- **No automatic data sampling:** schema refresh reads metadata only. Future AI
  drafting may use names, comments, types, and relationships, but sample values
  require a separate explicit opt-in design.
- **Database defense in depth:** recommend a dedicated read-only Postgres user;
  also execute each query in a read-only transaction with server-side limits.
- **No raw result retention:** chat can consume approved query results, but
  connector audit rows store redacted query structure and execution metadata,
  never result rows or plaintext filter values.

## Non-goals

- MySQL, MongoDB, and SQLite schema synchronization in this plan.
- Writes, DDL, stored procedure calls, or multiple SQL statements.
- Free-form SQL entered or generated by the model.
- Cross-connector joins or more than one connector per chat thread.
- Row-level security policy authoring for the external database.
- Automatic semantic descriptions based on unreviewed table contents.
- Saved metrics, dashboards, scheduled queries, ingestion, or embedding database
  rows in the first release.

## Data model

All mutable/readable records must carry `workspaceId` and be authorized through
the authenticated user's active workspace. A connection id by itself is never
sufficient authorization.

### `connector_schema_syncs`

One immutable record per refresh attempt:

- `id`, `workspaceId`, `connectionId`, `status` (`running | succeeded | failed`)
- `schemaHash`, counts for tables/columns/relationships
- `startedAt`, `completedAt`, `errorCode`, sanitized `errorMessage`
- `createdBy`

Use this for refresh state and history. Do not store credentials or raw driver
errors. Only one refresh may run for a connection at a time.

### `connector_tables`

Current discovered identity and physical metadata:

- `id`, `workspaceId`, `connectionId`
- `schemaName`, `tableName`, `databaseComment`, `estimatedRowCount`
- `lastSeenSyncId`, `lastSeenAt`, `removedAt`, `createdAt`, `updatedAt`
- Unique `(connectionId, schemaName, tableName)`
- Index `(workspaceId, connectionId, removedAt)`

The first release discovers base tables only. Views can be added later after
their read and security behavior is explicitly designed.

### `connector_columns`

Current discovered column metadata:

- `id`, `workspaceId`, `connectionId`, `tableId`
- `columnName`, `ordinalPosition`, `nativeType`, normalized type category
- `isNullable`, `defaultExpression`, `databaseComment`
- `isPrimaryKey`, `isUnique`
- `lastSeenSyncId`, `lastSeenAt`, `removedAt`, `createdAt`, `updatedAt`
- Unique `(tableId, columnName)`

Default expressions are display-only metadata and are never executed by this
application.

### `connector_relationships`

Discovered foreign keys and workspace-authored join hints:

- `id`, `workspaceId`, `connectionId`
- Source table/column and target table/column ids
- `origin` (`foreign_key | manual`), optional constraint name
- `description`, `enabled`, `lastSeenSyncId`, `removedAt`
- Unique discovered relationship identity per connection/constraint

Only enabled relationships may be used by the query compiler. A manual
relationship must reference active columns in the same connection and declare
cardinality when known (`one_to_one | one_to_many | many_to_one | unknown`).

### `connector_table_contexts`

Human-authored semantics and table-level execution policy:

- `tableId` (one-to-one), `workspaceId`, `connectionId`
- `description`, `synonyms` (JSON string array)
- `aiEnabled` (default false), `joinsEnabled` (default false)
- `maxRows` (default 100, hard application cap 200)
- `reviewedAt`, `reviewedBy`, `createdAt`, `updatedAt`

Descriptions have a bounded length and synonyms are normalized, deduplicated,
and capped. Enabling a table records who reviewed it and when.

### `connector_column_contexts`

Human-authored semantics and column-level execution policy:

- `columnId` (one-to-one), `workspaceId`, `connectionId`, `tableId`
- `description`, `synonyms` (JSON string array)
- `aiEnabled` (default true while the parent table remains disabled)
- `sensitive` (default false), `allowedOperations` (validated JSON enum array)
- `reviewedAt`, `reviewedBy`, `createdAt`, `updatedAt`

Supported operations are `select`, `filter`, `sort`, `group`, and `aggregate`.
Marking a column sensitive disables AI access until a user explicitly re-enables
it after acknowledging the warning. The UI may flag likely-sensitive names as a
review hint, but heuristics must never claim to classify data reliably.

### `connector_query_audit_logs`

Immutable audit record for attempted tool execution:

- `id`, `workspaceId`, `connectionId`, `threadId`, `userId`
- `toolName`, referenced table/column ids, redacted query shape
- `status` (`succeeded | rejected | failed | timed_out`), refusal/error code
- `durationMs`, `rowCount`, `resultBytes`, `truncated`, `createdAt`

Do not store result rows, generated SQL, credentials, or plaintext filter values.
Store operators and value types only in the redacted query shape.

### Chat thread binding

Add nullable `connectionId` to `chat_threads` with `ON DELETE SET NULL`, plus an
index. Existing threads remain knowledge-base-only. A thread can select only an
active, connected, Postgres connection in its workspace.

## Schema synchronization

Replace live table-name-only browsing with persisted metadata. Keep the driver
boundary under `lib/connectors/` so future database types can implement the same
normalized result contract.

For Postgres, introspect in bounded catalog queries:

- Base tables and database comments.
- Columns, native types, nullability, defaults, ordinal positions, and comments.
- Primary keys and unique constraints.
- Foreign-key constraints and their ordered column mappings.
- Optional planner row estimates, clearly labeled approximate.

Refresh behavior:

1. Authorize `connectionId + workspaceId` and reject deleted/non-Postgres records.
2. Acquire a per-connection refresh lock or reject an overlapping refresh.
3. Decrypt credentials only immediately before opening the external connection.
4. Apply connect, statement, total-duration, object-count, and response-size caps.
5. Build a normalized snapshot and deterministic hash.
6. In one local transaction, upsert seen objects and mark missing objects removed.
7. Preserve all table/column context records across refreshes.
8. Disable removed tables/relationships for AI execution.
9. Record a sanitized sync result and close the external client in `finally`.

Initial limits:

- 3-second connect timeout and 15-second schema refresh timeout.
- 500 tables, 10,000 columns, and 5,000 relationships per connection.
- Reject and report a clear limit error rather than silently storing a partial
  schema.

The existing `Promise.race` timeout does not cancel driver work. Replace it with
Postgres `statement_timeout` plus an abort/cancellation-capable lifecycle where
supported; always close the client.

## API surface

Add typed endpoint builders, fetchers, query keys, and mutations under
`api/connections/`, registered in `api/endpoints.ts`.

- `GET /api/connections/:id/schema` - paginated persisted tables with sync state,
  review state, and enabled counts; filters for active/removed and enabled/disabled
- `POST /api/connections/:id/schema/refresh` - run a bounded metadata refresh;
  return sync summary
- `GET /api/connections/:id/schema/tables/:tableId` - table detail with paginated
  columns, relationships, and contexts
- `PATCH /api/connections/:id/schema/tables/:tableId/context` - update description,
  synonyms, and table policy
- `PATCH /api/connections/:id/schema/columns/:columnId/context` - update column
  description and policy
- `POST /api/connections/:id/schema/relationships` - create a manual relationship
- `PATCH /api/connections/:id/schema/relationships/:relationshipId` - update or
  enable/disable a relationship
- `DELETE /api/connections/:id/schema/relationships/:relationshipId` - delete only
  manual relationships; discovered relationships can only be disabled
- `PATCH /api/chat/threads/:id/connection` - select or clear one authorized
  connector for the thread

Every route must:

- Resolve the authenticated user and active workspace.
- Scope the connection and every child id to that workspace and connection.
- Use shared Zod schemas on both client and server where practical.
- Return stable application error codes and sanitized messages.
- Cap pagination and reject unknown fields or operations.
- Invalidate only affected connection schema, detail, and thread query keys.

The old `/tables` endpoint can read from persisted metadata after the first
successful refresh. Remove it once the detail page uses `/schema`; no long-term
compatibility layer is required because there are no external consumers.

## Connector detail UI

Refactor `agent-connector-detail.tsx` before it approaches the 250-line ESLint
limit. Suggested components:

- Connector header with status, last schema refresh, and Refresh schema action.
- Summary cards: discovered, enabled, needs review, removed, last refresh result.
- Searchable/filterable paginated table list.
- Table detail panel/page with physical schema, context, columns, and joins.
- Table context form for description, synonyms, AI access, joins, and row cap.
- Column table with inline policy controls and a focused description editor.
- Relationship list separating discovered keys from manual join hints.
- Removed-object view showing schema drift without offering AI enablement.

UX rules:

- A user must review table and column policy before enabling a table.
- Enabling joins requires at least one enabled relationship.
- Sensitive and likely-sensitive columns show a clear warning.
- Schema refresh never overwrites unsaved context; disable refresh while a context
  mutation is pending or warn before discarding local edits.
- Show database comments as discovered metadata, separate from editable business
  descriptions.
- Long forms use a constrained dialog with fixed header/footer and scrollable body.

## Structured AI tools

Expose a small generic set only when the thread has an authorized connector:

### `listDatabaseTables`

Returns enabled table ids/names, concise descriptions, and synonyms. It must not
return disabled or removed objects.

### `describeDatabaseTable`

Input: enabled table id. Returns enabled columns, types, descriptions, approved
operations, and enabled relationships. It must omit sensitive/disabled columns.

### `queryDatabase`

Accept a structured Zod-validated query specification:

- One required base table id.
- Selected column ids.
- Filters using approved operators and parameter values.
- Sorts and capped limit.
- Optional joins identified by approved relationship ids.
- Optional groupings and aggregates (`count`, `sum`, `avg`, `min`, `max`).

Do not let the model provide schema names, table names, column names, SQL
fragments, functions, casts, or operators outside the validated enums.

## Query compiler and execution policy

Implement a server-only compiler under `lib/connectors/query/`:

1. Resolve all ids from persisted metadata scoped to workspace and connection.
2. Reject removed/disabled tables, columns, relationships, and operations.
3. Validate aggregate compatibility against normalized data types.
4. Permit joins only through an enabled relationship and only when joins are
   enabled for every involved table.
5. Quote resolved Postgres identifiers with the driver utility; never interpolate
   model-supplied identifiers.
6. Bind every filter value as a Postgres parameter.
7. Append a server-controlled limit no higher than the strictest table policy and
   global cap.
8. Execute `BEGIN READ ONLY`, set local statement/lock/idle timeouts, run the
   statement, then `COMMIT`; use `ROLLBACK` on all errors.
9. Enforce row and serialized-byte caps before returning a structured result.
10. Return columns, normalized values, row count, truncation, duration, and
    warnings; never return raw driver errors.

Initial execution limits:

- 5-second statement timeout and 8-second total tool timeout.
- Default 50 rows, maximum 200 rows.
- Maximum 256 KB serialized result returned to the model.
- Maximum 3 joined tables, 20 selected columns, 10 filters, 5 sorts, and 5
  aggregate expressions.
- No offset-based unbounded scans; add cursor pagination later if needed.

Postgres read-only transactions are an application safeguard, not a substitute
for database permissions. The connection UI should recommend and detect, where
practical, a read-only login and display a warning when that cannot be confirmed.

## Chat integration

- Extend thread APIs/UI to select or clear one connector.
- Authorize the thread and connector together before constructing tools.
- Keep knowledge-base tools available; update the system prompt to distinguish
  sourced database answers from knowledge-base answers.
- Build compact tool descriptions from enabled semantic context instead of
  injecting the full schema into every system prompt.
- Require the model to call a connector tool before making factual claims about
  database contents and to mention truncation or query warnings.
- Keep the existing tool-step cap initially; observe whether database questions
  need a narrowly increased cap.
- Record connector tool execution in `connector_query_audit_logs`; generic chat
  audit may retain tool metadata but must not duplicate raw result rows.
- If the selected connector becomes deleted, disconnected, or has no enabled
  tables, omit query tools and return an actionable unavailable state.

## Security and privacy checklist

- [ ] Authorize workspace membership for every schema/context/query operation.
- [ ] Verify every nested table/column/relationship belongs to the same connection.
- [ ] Decrypt credentials only server-side and only for refresh/query execution.
- [ ] Harden host resolution against metadata hosts, private-range policy bypass,
      DNS rebinding, and IPv6 variants before expanding production access.
- [ ] Use a dedicated external read-only database role in setup guidance.
- [ ] Reject writes, DDL, functions, raw expressions, comments, and multi-statements
      by construction rather than keyword filtering.
- [ ] Parameterize all values and quote only server-resolved identifiers.
- [ ] Enforce external statement timeout plus application total timeout.
- [ ] Cap schema objects, joins, filters, rows, bytes, and tool steps.
- [ ] Sanitize all external driver errors before API/model/UI exposure.
- [ ] Never audit credentials, raw SQL, result rows, or plaintext filter values.
- [ ] Omit disabled/sensitive metadata from model-visible tool results.
- [ ] Automatically disable missing schema objects after refresh.
- [ ] Ensure connection soft delete makes schema and query APIs unavailable.

## Acceptance criteria

- A Postgres connector can refresh and persist tables, columns, constraints, and
  foreign-key relationships without overwriting semantic context.
- Schema additions/removals are visible, and removed objects cannot be queried.
- A user can describe and govern each table/column and explicitly enable it.
- A chat thread can use one workspace-authorized connector.
- The model sees only enabled, active, non-sensitive metadata.
- Database questions execute only through the structured query schema.
- All query values are bound parameters; all identifiers come from authorized
  persisted metadata.
- Writes and arbitrary SQL are impossible through the exposed tool contract.
- Query duration, rows, bytes, joins, filters, and tool steps are bounded.
- Every attempt has a redacted connector audit record, with no raw results.
- Existing knowledge-base-only chat and connector CRUD continue to work.
